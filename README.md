# EDMD-Framework

**An event-driven medallion architecture with domain-driven design for training-serving consistent credit risk feature engineering**

Akshay Sharma · akshay.sharma1088@gmail.com · Code and data for the manuscript submitted to *PeerJ Computer Science* (AI Application).

## Description

EDMD combines three ideas for building credit-risk features in production:
- event-driven processing with lateness bounds calibrated per event class
- domain-driven design, with bounded contexts and anti-corruption layers between data domains
- a four-tier medallion architecture (Bronze, Silver, Gold and a model-ready Platinum tier)

This repository contains everything needed to reproduce the paper's results:
- a synthetic event-stream generator
- the behavioral feature pipeline
- the risk-constrained threshold calibration algorithm
- a population-drift monitor
- the simulation benchmark that compares EDMD with a feature store, Kappa, a three-tier medallion and Lambda

## Dataset Information

No real customer or institution data are used. All data are synthetic and generated by code in this repository.

- **Benchmark data.** `src/evaluation/simulation_benchmark.py` generates its own event stream for each random seed. Each stream has 50,000 accounts by default, with a latent risk factor, four event classes (transaction, payment, bureau refresh, account change), an event time and an arrival time per event, and a default label driven by the same latent factors as behavior. A configurable share of events arrives late (1%, 5%, 10% and 20% in the paper).
- **Demonstration data.** `src/data/synthetic_generator.py` writes an event stream to Parquet for the feature pipeline and the drift monitor.
- **Feature specification.** `artifacts/feature_spec.yaml` documents each feature's definition, window and event class.
- **Archived results.** The paper's numbers are in `artifacts/simulation/`:
  - `main_runs.json`: per-seed results
  - `summary.csv`: mean and standard deviation per architecture and metric
  - `late_rate_sensitivity.csv`
  - `kappa_sensitivity.json`
  - `figure4.png`

## Usage Instructions

```bash
git clone https://github.com/akshaysharma1088/EDMD-Framework.git
cd EDMD-Framework
pip install -r requirements.txt

# Reproduce the benchmark tables (about 5 minutes on 2 CPUs) and Figure 4
python src/evaluation/simulation_benchmark.py --output_dir artifacts/simulation
python src/evaluation/plot_figure4.py artifacts/simulation/main_runs.json artifacts/simulation/figure4.png

# Optional: run the feature pipeline and drift monitor on a small synthetic stream
python src/data/synthetic_generator.py --n_accounts 1000 --daily_events 10000 \
    --simulation_days 3 --output_path artifacts/synthetic_events.parquet --seed 42
python src/data/feature_engineering.py --events_path artifacts/synthetic_events.parquet \
    --output_path artifacts/feature_store.parquet --decision_date 2024-04-01
python src/monitoring/drift_monitor.py --reference_path artifacts/feature_store.parquet \
    --current_path artifacts/feature_store.parquet --output_path artifacts/psi_report.json
```

With Docker:

```bash
docker build -t edmd-framework -f docker/Dockerfile .
docker run -v "$(pwd)/artifacts:/app/artifacts" edmd-framework
```

## Methodology

1. **Data generation and preprocessing.** For each seed, the benchmark draws accounts and events, assigns each event an event time and an arrival time, and injects late arrivals at the configured rate. There is no cleaning step, because the data are generated in the required form. Features are computed over event-time windows (3, 6 and 12 months) at a fixed decision date.
2. **Architectures as event-inclusion rules.** Each architecture is modeled by the rule that decides which events contribute to a feature on three paths:
   - **training:** the value the training pipeline produces
   - **serving:** the value available to the scoring service at decision time
   - **eventual:** the value the serving store holds after any recovery or correction

   The same feature definitions are applied to every architecture. No streaming engine is run, so latency is not measured.
3. **Evaluation and benchmark comparison.** Five architectures (EDMD, feature store, Kappa, three-tier medallion, Lambda) plus an oracle with complete features are compared over five seeds:
   - **Training-serving skew (TSS):** the mean absolute difference between training and serving values, normalized by each feature's standard deviation.
   - **Serving error (SERR):** the same measure, comparing served values with the complete features.
   - **Late-event recovery (LERR):** the share of late events eventually reflected, macro-averaged over event classes.
   - **AUC:** from an XGBoost model trained on training-path features and scored on serving-path features of held-out accounts.

   Sensitivity analyses vary the late-event rate and Kappa's allowed lateness.

### Headline results (50,000 accounts, 5 seeds, 10% late events)

| Architecture | TSS | SERR | LERR | AUC |
|---|---|---|---|---|
| EDMD | 0.000 | 0.057 | 1.000 | 0.856 ± 0.006 |
| Feature store | 0.057 | 0.057 | 1.000 | 0.853 ± 0.006 |
| Kappa (72 h allowed lateness) | 0.009 | 0.169 | 0.500 | 0.853 ± 0.005 |
| Three-tier medallion | 0.032 | 0.182 | 0.599 | 0.853 ± 0.006 |
| Lambda | 0.064 | 0.064 | 1.000 | 0.853 ± 0.006 |
| Oracle (complete features) | n/a | 0 | n/a | 0.857 ± 0.007 |

EDMD's zero skew follows by construction from training on the as-served Platinum values. The AUC differences between architectures are small.

> **Earlier versions.** Earlier versions of this repository shipped `src/evaluation/benchmark.py`, which reported preset values with added noise rather than measured results. It has been removed; all results now come from `simulation_benchmark.py`.
